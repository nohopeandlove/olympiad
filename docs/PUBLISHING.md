# Запуск по постоянной ссылке и работа через dev

Для постоянной ссылки нужны домен и VPS — арендованный Linux-компьютер, работающий круглосуточно. Docker Desktop на домашнем компьютере остаётся для разработки; работа публичного сайта не зависит от его включения.

Сервер и домен ещё не приобретены. Ниже — подготовленная конфигурация, а не уже опубликованный сайт. Пример `olympiad.example.org` нужно заменить вашим настоящим доменом.

## Что приобрести

1. Домен у любого регистратора. Организатор также может выдать поддомен своего существующего сайта — тогда отдельная покупка домена не нужна.
2. VPS сайта: Ubuntu 24.04 LTS, ориентир для небольшого запуска — 2 vCPU, 4 ГБ RAM, 40 ГБ SSD, публичный IPv4.
3. Отдельный VPS проверки Python: Ubuntu 24.04 LTS, ориентир — 2 vCPU, 4 ГБ RAM, 30 ГБ SSD, публичный IPv4. Он нужен потому, что выполняет программы участников и имеет доступ к Docker. На нём нет базы и персональных данных сайта. По умолчанию одновременно проверяются две программы; количество ресурсов уточняется после нагрузочной проверки.
4. Почтовый ящик/SMTP-служба с отправкой через порт 587 и STARTTLS. Mailpit из development не доставляет письма в настоящие почтовые ящики. Получите SMTP host, логин, пароль приложения и разрешённый адрес отправителя у почтового провайдера. Пароли не передавайте в чат и GitHub.

## Настроить DNS

В панели DNS добавьте A-записи:

| Имя | Значение |
|---|---|
| `@` (основной домен) | Публичный IPv4 VPS сайта |
| `judge` | Публичный IPv4 VPS проверки Python |

Если используете поддомен техникума, администратор его DNS создаёт соответствующие записи. В таком случае SITE_DOMAIN — весь поддомен, JUDGE_DOMAIN — выбранный отдельный адрес проверки.

Оставьте записи в режиме DNS only, без проксирования CDN. Не добавляйте AAAA, если IPv6 не настроен. Пример использует сайт без `www`. Сертификаты HTTPS Caddy получает и продлевает автоматически после появления правильных DNS-записей и доступности портов 80/443. До этого публичный HTTPS не заработает.

## Подготовить оба VPS

Подключитесь по SSH из PowerShell, используя адрес и пользователя, выданные хостингом:

```powershell
ssh root@IP_СЕРВЕРА
```

Далее команды выполняются **в Linux-терминале VPS**, не локально в Windows. Установите Git и Docker Engine с плагином Compose по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Нужен Compose версии 2.24.4 или новее для production override. Проверьте:

```bash
docker version
docker compose version
git --version
```

В сетевой панели хостинга разрешите SSH только для администраторов, HTTP 80 и HTTPS 443. База, Redis, backend и сам judge не публикуют свои порты. Внешние запросы к judge дополнительно ограничиваются IP сайта в Caddy и общим случайным токеном; worker проверяет настоящий TLS-сертификат judge. Внутри sandbox сетевого доступа нет.

Клонируйте репозиторий на оба VPS, используя GitHub-доступ своей учётной записи, если репозиторий приватный:

```bash
git clone https://github.com/nohopeandlove/olympiad.git
cd olympiad
git switch main
```

Новые файлы настройки сейчас находятся в `dev`: прежде чем запускать публичный сайт из `main`, проверьте и слейте pull request `dev → main`. Не включайте автоматическое развёртывание `dev` на рабочем сервере.

## Сначала запустить отдельную проверку Python

На VPS проверки:

```bash
cp .env.judge.example .env.judge
chmod 600 .env.judge
openssl rand -hex 32
nano .env.judge
```

Заполните JUDGE_DOMAIN (например, `judge.olympiad.example.org`), ACME_EMAIL (ваша почта), APP_SERVER_IP (публичный IPv4 VPS сайта). Результат `openssl` сохраните как JUDGE_TOKEN — его же потребуется указать на VPS сайта. Используйте разные случайные значения для токена judge и пароля базы.

```bash
docker compose -p olympiad-judge --env-file .env.judge -f compose.judge.yaml up --build -d
docker compose -p olympiad-judge --env-file .env.judge -f compose.judge.yaml logs --tail=50 caddy
```

Доступ к службе проверки с вашего домашнего компьютера обычно вернёт 403: разрешён IP VPS сайта. HTTP перенаправляется на HTTPS. Данные базы и SMTP на этот сервер не копируются.

## Затем запустить сайт

На VPS сайта:

```bash
cp .env.production.example .env.production
chmod 600 .env.production
openssl rand -hex 32
nano .env.production
```

Заполните SITE_DOMAIN (ваш домен без `https://`), ACME_EMAIL, POSTGRES_PASSWORD (новое случайное hex-значение), JUDGE_TOKEN (то же, что на judge), SMTP_HOST, SMTP_FROM, SMTP_USER и SMTP_PASSWORD. PUBLIC_ORIGIN и JUDGE_URL в примере строятся из SITE_DOMAIN; если адрес judge выбран иначе, укажите его полным HTTPS-адресом. PUBLIC_ORIGIN — точный адрес сайта без завершающего `/` и без дополнительного пути.

В текущем терминале удобно определить функцию для правильного набора Compose-файлов:

```bash
dc() {
  docker compose -p olympiad --env-file .env.production \
    -f compose.yaml -f compose.production.yaml "$@"
}
dc up --build -d
dc exec backend python -m app.create_admin
```

Последняя команда интерактивно создаёт администратора. **Development seed не запускайте**: он создаёт публично известные тестовые аккаунты. На новой production-базе миграции сами устанавливают приключение, но организатор ещё должен проверить даты регистрации и этапов, а затем открыть олимпиаду в админке. Не копируйте домашнюю development-базу на публичный сервер.

Ссылка после настройки: `https://ВАШ_ДОМЕН`. Нужен один адрес — по нему открываются сайт, регистрация и личный кабинет. Проверка Python работает через отдельный адрес в фоне, участникам он не нужен.

После запуска проверьте с отдельного тестового аккаунта: регистрацию, доставку настоящего письма, вход, расписание, отправку Python-программы и её Accepted; обе категории и письменный вопрос. Также проверьте создание и восстановление резервной копии. Перед массовым приглашением участников организатор должен утвердить правила и документы для обработки данных и несовершеннолетних; шаблоны разработки их не заменяют.

Полный публичный запуск, получение сертификата и доставка настоящей SMTP-почты в облачной среде Codex не проверены: для этого ещё нет ваших VPS, DNS и почтовых настроек. Compose-конфигурации и Caddy проверяются отдельно без публикации.

## dev и main

- `dev` — разработка и проверка изменений.
- `main` — версия для рабочего сайта.
- Pull request `dev → main` — просмотр и проверка изменений перед выпуском.
- GitHub Actions автоматически запускает **Backend checks** и **Frontend build** при push и pull request. Эти проверки проверяют схемы, задания, обновление контента, время и сборку интерфейса. Реальный SMTP, Docker judge, регистрация и браузерный путь требуют отдельной проверки на development-установке.
- Изменения не разворачиваются на VPS автоматически. После одобренного слияния обновление выполняется явно с резервной копией.

В GitHub откройте **Settings → Rules → Rulesets** (или **Branches → Add branch protection rule**). Создайте правило для `main`: требовать pull request, успешные status checks **Backend checks** и **Frontend build**, запретить force push и удаление ветки. Дождитесь первого запуска Actions, чтобы проверки появились в списке. Если тариф GitHub не позволяет включить ограничения для приватного репозитория, сохраните тот же порядок вручную; один только файл workflow не запрещает прямой push. Настройки защиты ещё не включены из Codex.

Для просмотра `dev` на вашем компьютере из папки проекта (первый раз):

```powershell
git fetch origin
git switch --track origin/dev
```

При следующих обновлениях:

```powershell
git switch dev
git pull --ff-only
```

Ваш обычный локальный Compose-запуск можно сохранить. Имя Compose-проекта (`olympiad-main`) не выбирает Git-ветку — это только имя контейнеров и томов. Не запускайте несколько локальных копий на одном порту одновременно. Для тестов используйте только development-данные, отдельно от рабочей базы.

## Обновлять рабочий сайт после слияния

На VPS сайта, из его папки `olympiad`, снова определите функцию `dc` выше. Сначала сделайте резервную копию, затем обновите `main`:

```bash
mkdir -p backups
chmod 700 backups
umask 077
dc exec -T postgres pg_dump -U olympiad -d olympiad -Fc > "backups/olympiad-$(date -u +%Y%m%dT%H%M%SZ).dump"
git switch main
git pull --ff-only
dc up --build -d
```

Храните зашифрованную копию также вне VPS. Не используйте `docker compose down -v`: это удаляет данные. Для обновления judge выполните на его отдельном VPS `git switch main`, `git pull --ff-only` и прежнюю команду запуска из раздела judge. На время обслуживания в середине этапа остановите постановку новых проверок или согласуйте время вне соревнования.

Если выпуск сломался, сначала изучите логи и миграции. Возврат к предыдущему коммиту кода сам по себе не откатывает базу. Автоматический сброс попыток, обратные миграции и восстановление поверх рабочей базы не выполняются.
